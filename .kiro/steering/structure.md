# Structure — Skeleton Crew

The repo holds two apps: the harness (the safety gate itself) and the
demo crew (a scripted consumer that runs its tool calls through the
gate). Shared runtime output and config live at the root.

```
skeleton-crew/
├── .kiro/
│   ├── settings/
│   │   └── mcp.json          # MCP servers for Kiro (none configured yet)
│   └── steering/
│       ├── product.md        # what the harness is and who it serves
│       ├── tech.md           # stack, design rules, commands
│       └── structure.md      # this file
├── apps/
│   ├── harness/              # App 1 — the safety gate
│   │   ├── harness.js        # the policy gate: evaluate / execute / audit
│   │   ├── policy.js         # policy files: loadPolicy / validatePolicy
│   │   ├── approver.js       # interactive terminal approver for HELD calls
│   │   ├── report.js         # audit-report command (npm run report)
│   │   └── test/
│   │       ├── harness.test.js   # node:test decision + audit tests
│   │       ├── policy.test.js    # policy-file loading + strict validation
│   │       ├── report.test.js    # audit summary + veto list + report CLI
│   │       └── approver.test.js  # terminal approver + fail-closed tests
│   └── demo-crew/            # App 2 — the demo crew (consumer of the gate)
│       └── demo.js           # scripted 3-agent crew demo (npm run demo)
├── logs/
│   └── audit.jsonl           # generated by the demo (gitignored)
├── policy.example.json       # example policy file (= built-in defaults)
├── package.json
├── README.md
└── LICENSE
```

## Where things belong

- New policy rules go in `Harness.evaluate()` in
  `apps/harness/harness.js`, in deny → injection → hold order, each
  returning explicit reasons.
- New approvers go in `apps/harness/approver.js` (or a sibling module
  in `apps/harness/`) behind the same contract — async
  (call, reasons) => boolean, fail closed on any non-answer — and are
  wired into the harness, never around it.
- New demo agents or scenarios go in `apps/demo-crew/demo.js` as
  additional calls through the same harness — never bypass it.
- New behaviour gets a test in `apps/harness/test/` first: one test
  per decision path (allow, hold-approved, hold-declined, deny).
- Runtime output (audit logs) goes under `logs/` and is never
  committed.
